# 장르 취향 추천 검증 기록

## 결론

**작성자 계정에서 기존 "긍정 비율 높은순"(Steam 리뷰) 정렬 대비 추가 가치를 입증하지 못했다.**

그래서 장르 레벨만 공개하고, 장르 취향과 그 위에 만든 기능은 보류한다
(`GENRE_TASTE_ENABLED = false`, `app/genres.ts`). 보류 대상은 다음 네 가지다.

- 레벨 팝업의 "장르 선호도" 탭
- 레벨 배지의 "선호 1위" 툴팁
- 위시리스트의 "추천도 높은순" 정렬
- 추천 칩

추천 계산 개선(시간 상한, 태그 제외 등)도 미뤘다. 계산 코드와 테스트는 그대로 남겨 두었다.

- 검증일: 2026-10-18
- 대상: `feature/genre-leveling`의 `computeGenreTaste`, `recommendScore`
- 판단: Claude와 Codex가 함께 검토했고, 공개 범위는 사용자가 결정했다.

## 측정 방법

- **정답**: 사용자가 이미 플레이하고 평가한 게임의 평가.
  - 좋아함: 추천이고, 별점이 4개 이상이거나 없음.
  - 싫어함: 하차, 비추천, 또는 별점 2개 이하.
- **절차(leave-one-out)**: 평가한 게임을 하나씩 빼고 나머지로 장르 취향을 다시 계산한 뒤, 뺀 게임의 추천 점수를 구한다.
  그 게임 자신의 평가가 점수에 섞이지 않게 하려는 것이다.
- **지표**: AUC. 좋아한 게임의 점수가 싫어한 게임보다 높을 확률이다(0.5 = 무작위).
- **비교 대상**:
  - 태그 목록: 현재 / 인디·어드벤처·캐주얼을 하나씩 제외 / 셋 다 제외
  - 게임당 시간 가중치(장르 평균과 개인 평균에 똑같이 적용): 현재(시간 그대로) / 50시간 상한 / 20시간 상한 / 제곱근 / 게임별 동일
  - 기준선: Steam 리뷰 긍정 비율, 그리고 리뷰와 취향을 z-점수로 바꿔 합친 값
- **재구현 검증**: 스크립트가 다시 짠 취향 계산은 "현재 / 현재" 조합에서 `computeGenreTaste`와 정확히 같은 값을 낸다. 스크립트가 매번 확인한다.

## 결과 (작성자 계정)

- 라이브러리 566개(플레이 기록 474개), 위시리스트 887개
- 취향 집계 대상 265개. 그중 좋아함 164개, 싫어함 63개
- sync 데이터는 이전 방식의 통째 레코드에서 읽었다.

| 태그 \ 가중치 | 시간(현재) | 상한 50h | 상한 20h | 제곱근 | 동일  |
| ------------- | ---------- | -------- | -------- | ------ | ----- |
| 현재 태그     | **0.501**  | 0.579    | 0.584    | 0.561  | 0.587 |
| 인디 제외     | 0.516      | 0.590    | 0.591    | 0.574  | 0.590 |
| 어드벤처 제외 | 0.534      | 0.579    | 0.581    | 0.560  | 0.563 |
| 캐주얼 제외   | 0.530      | 0.585    | 0.585    | 0.567  | 0.589 |
| 셋 다 제외    | 0.577      | 0.598    | 0.593    | 0.580  | 0.585 |

| 기준선                             | AUC           |
| ---------------------------------- | ------------- |
| Steam 리뷰 긍정 비율 (취향 미사용) | **0.655**     |
| 리뷰 + 취향 (취향 비중 0.25)       | 0.661 ~ 0.664 |
| 리뷰 + 취향 (취향 비중 0.5)        | 0.648 ~ 0.657 |

AUC 표준오차는 약 ±0.04다.

### 해석

- **현재 설계는 무작위 수준이다(0.501).** 가장 큰 원인은 시간 가중치다. 장시간 게임 몇 개가 장르 평균을 결정한다.
  시간 상한만 둬도 0.58 안팎으로 오른다.
- **흔한 태그 제외는 시간 가중치를 그대로 둘 때만 효과가 크다(0.501 → 0.577).**
  시간 상한을 둔 뒤에는 차이가 0.02 이내라 오차 범위다. 흔한 태그를 주원인으로 보기 어렵다.
- **개선한 최선의 조합(약 0.60)도 리뷰 긍정 비율(0.655)보다 낮다.** 둘을 합쳐도 오차 범위 안이다.
  이 계정에서는 장르 취향이 리뷰 정렬 이상의 정보를 주지 못했다.
- 위시리스트 라벨의 동점 처리를 평균 순위로 바꿔도 이 계정의 라벨 분포는 같았다(잘 맞음 102 / 보통 486 / 안 맞음 296).
  다만 전부 동점일 때 모두 "잘 맞음"이 되는 경계 사례는 남아 있다.

### 한계

- 계정 1개이고, 싫어함 표본이 63개다.
- 이미 플레이한 라이브러리 게임으로 측정했다. 실제 추천 대상인 아직 안 한 위시리스트 게임과는 분포가 다를 수 있다.
- Steam 리뷰 비율은 측정 시점 값이고, 정답 라벨은 사용자의 평가 습관에 따라 달라진다.

## 다시 검토할 조건

다음 중 하나가 생기면 같은 스크립트로 다시 측정한다.

- 다른 계정, 특히 평가가 충분한 계정에서 결과를 확인할 수 있게 될 때.
- 같은 계정의 평가 데이터가 크게 늘어날 때. 기준: 싫어함 100개 이상.
- 추천 계산을 바꿨을 때. 공개 기준은 **리뷰 기준선보다 표준오차 이상 높을 것**이다.

## 재현 방법

읽기 전용이다. Steam API와 Upstash에서 읽기만 하고, 아무 데도 쓰지 않는다.
`/api/sync` 경로를 거치지 않고 Redis를 직접 GET하는데, 그 경로는 첫 접근 때 이전 레코드를 변환하면서 쓰기를 하기 때문이다.

```sh
# .env.local 에 STEAM_API_KEY, UPSTASH_REDIS_REST_URL, UPSTASH_REDIS_REST_TOKEN 필요
EVAL_STEAM_ID=<17자리 SteamID64> npx vitest run --config tools/taste-eval/vitest.config.ts
```

- 결과: `tools/taste-eval/out/result-<id>.md`
- 원본 데이터 캐시: `tools/taste-eval/out/data-<id>.json`
  - 캐시가 있으면 API를 다시 부르지 않는다.
  - 최신 데이터로 다시 재려면 이 캐시를 지운다.
- `tools/taste-eval/out/`에는 계정의 라이브러리와 평가가 들어 있어서 gitignore 처리되어 있다.
- 출력 위치는 `EVAL_OUT`으로 바꿀 수 있다.
- 이 스크립트는 루트 vitest 설정(`tests/**`)에 포함되지 않으므로 `npm test`와 CI에서 실행되지 않는다.
